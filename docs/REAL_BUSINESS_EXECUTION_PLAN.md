# 真实业务化执行计划（单场景：护肤咨询到购物车草稿）

## 目标与证据

本计划只把一个用户可完成的结果做实：用户提交肤况与预算，获得有审核资料依据的推荐；用户显式确认后，系统二次校验可售状态并创建**购物车草稿**。草稿不是订单、更不是支付或自动购买。

现有实现已具备 FastAPI POST SSE、LangGraph 路由、安全停荐、证据过滤、确认令牌与前端确认卡；但运行轨迹、令牌、草稿和审计都在进程内，重启会丢失，商品与资料也是仿真数据。因此本阶段的关键验收不是“回答更像真人”，而是“确认后的可见结果有可回查、可恢复的持久记录”。

## 已批准范围

| 范围 | 本阶段行为 | 权威方 |
| --- | --- | --- |
| 推荐与安全路由 | 继续由现有确定性策略与 LangGraph 执行 | 护肤助手服务 |
| 价格、库存、上架、审核 | 继续只读；通过 `Catalog` 适配器获取 | 商城商品/库存服务（接入前为明确标记的仿真源） |
| 资料检索 | 仅已审核、上架资料进入检索和模型上下文 | 内容运营/知识审核 |
| 确认令牌、运行轨迹、审计、模型用量、草稿 | 使用 SQLite 持久化，支持重启后回查与一次性消费 | 护肤助手服务 |
| 购物车草稿 | 仅创建助手侧草稿回执；后续替换为商城购物车写入适配器 | 商城购物车服务 |

## 明确不做

- 不诊断疾病、不承诺疗效。
- 不实现下单、支付、优惠、改价、库存变更或积分。
- 不把 RAG 文本作为价格、库存、支付或授权事实。
- 不伪造商城 API、用户身份、运营审核结果或生产数据。

## 关键状态与恢复

| 状态 | 用户可见结果 | 服务端持久化 | 恢复/下一步 |
| --- | --- | --- | --- |
| `running` / SSE 中 | 公开的检索与回答步骤 | run、审计、模型用量、trace | 网络中断后用 `run_id` 查询轨迹 |
| `approval_required` | 仅展示套餐与“确认加入草稿” | 有有效期的服务端令牌与套餐快照 | 用户确认、取消，或令牌过期后重新发起咨询 |
| `created` | 草稿 ID、二次校验时间 | 草稿、令牌已消费、审计 | 可查询草稿；不表示订单已提交 |
| 库存/上架变化 | 不显示成功 | 失败审计；令牌不误消费 | 前端提示重试或重新咨询 |
| 策略/安全拦截 | 停止推荐或请求补充 | trace、零调用用量记录 | 用户补充信息或转人工 |

## 实施顺序与验收

### 阶段 1：持久化业务边界（本次执行）

1. 新增 SQLite Repository，配置 `SKIN_ASSISTANT_DB_PATH`；测试默认使用内存库，部署可指定持久文件。
2. 持久化 `AgentTrace`、`AuditLog`、`ModelUsageLog`、确认令牌和购物车草稿；令牌必须有 TTL、只能成功消费一次。
3. 让 Service 使用 Repository，不改变 SSE 和前端已有数据契约。
4. 增加持久化回归：重建 Service 后仍能查 trace / 审计 / 用量；有效令牌只可创建一个草稿，过期令牌返回冲突。

验收：全量后端测试通过；安全分支不产生套餐或令牌；确认成功后重启服务仍可按 `run_id` 查到公开轨迹；重复确认不创建第二个草稿。

### 阶段 1.1：模型成本与超时护栏（本次执行）

1. `MODEL_MAX_CALLS_PER_RUN` 默认 1；图状态记录已消耗调用次数，即使未来新增循环节点也不能越过预算。
2. `MODEL_REQUEST_TIMEOUT_SECONDS` 默认 8 秒、SDK 重试固定为 0；超时返回确定性证据兜底，绝不自动发起第二次模型请求。
3. `LANGGRAPH_RECURSION_LIMIT` 默认 24，`AGENT_RUN_TIMEOUT_SECONDS` 默认 12；超出总运行时限的 SSE 明确结束为失败，不创建草稿。
4. 模型用量和 trace 记录 `model_call_count`、`model_call_budget` 与 timeout/fallback 原因，作为调参与灰度依据。

### 阶段 2：接入权威商城读模型（适配器已完成，等待测试环境配置）

1. 已给 `Catalog` 增加 `CATALOG_SOURCE=mall` 的 OAuth2 Client Credentials 只读适配器；候选读取不发送用户原文，只发送场景标签和 `request_id`。
2. 已加入超时、缺字段、陈旧库存、重复/遗漏 SKU 和鉴权失败的明确错误；配置缺失时启动失败，不回退 Mock。
3. 已用 `httpx.MockTransport` 覆盖候选、实时可售、重启后确认恢复、陈旧库存和配置缺失。待测试环境可用后补跑真实接口的缺货、下架、超预算和价格变更夹具。

剩余依赖：商城测试环境 URL、OAuth issuer/client、`TST-SKIN-*` 实际映射、刷新 SLA 的最终确认，以及商城团队提供的可控缺货/改价夹具。

### 阶段 3：内容审核与知识库运营化（依赖内容运营）

1. 将资料版本、审核人、上架状态和切块放入内容管理流程；对象存储与解析异步化。
2. 每个发布版本绑定检索索引与评测快照；召回、证据引用和安全硬门变化均跑黄金集和人工抽检。

### 阶段 4：商城草稿写入适配器与灰度

1. 增加已认证用户/访客会话、幂等键、商城草稿写入和可撤销/失效状态。
2. 只有商城返回明确草稿 ID 后才呈现成功；网络超时显示未知提交状态并按幂等键查询，绝不盲目重试写入。
3. 先灰度真实加购，再评估是否扩大范围；订单和支付仍保持独立边界。

## 部署与治理决策门

- 生产数据库使用受管 PostgreSQL；SQLite 是本阶段的本地/集成持久化实现，不是多实例生产替代品。
- 确认令牌 TTL、审计留存期、可查看轨迹的权限、用户标识方式和个人信息脱敏规则须由业务/安全负责人确认。
- 真实商品、库存、资料和购物车写入接通前，UI 与接口继续标明演练/草稿边界，不能宣称为商城真实交易。
